# Architecture

This document describes what the starter **implements today**. Anything a future product may need is recorded as a decision in [`docs/decisions/`](decisions/) and marked **not implemented**.

## Stack

| Concern | Implementation |
|---|---|
| Framework | Next.js 16 App Router, React 19, strict TypeScript, Node.js runtime (no static export) |
| Styling | Tailwind CSS 4 utilities on native elements; no component library or design system |
| Auth | Supabase Auth (email + password) via `@supabase/ssr` cookies |
| Database | Supabase Postgres; SQL migrations and pgTAP tests managed by the Supabase CLI; generated TypeScript types |
| i18n | `next-intl` with `en` (default, no URL prefix) and `es` (`/es/...`); dictionaries in `src/locales` |
| Validation | Zod at request boundaries (Server Actions, env) |
| Observability | LogTape JSON logs to stdout with field redaction; Sentry optional (off without a DSN) |
| Quality | Oxlint/Oxfmt (Ultracite presets), Knip, i18n-check, Vitest (unit + browser), Playwright (+ axe), Lefthook, commitlint |

## Code layout

```text
src/
  proxy.ts                    Session refresh + locale routing for every page request
  instrumentation*.ts         Optional Sentry initialization (server/edge/browser)
  actions/                    Server Actions: auth and profile mutations
  app/[locale]/
    (public)/                 Home, sign-in, sign-up, forgot-password (public shell)
    app/                      Protected area: profile, change password (app shell)
    auth/callback/route.ts    Email link (PKCE) code exchange
    not-found.tsx, [...rest]  Localized 404
  components/                 ActionForm (accessible form bound to a Server Action), LocaleSwitcher
  libs/                       Env, Supabase clients, Logger, Sentry options, i18n routing/navigation
  locales/                    en.json, es.json
  templates/BaseTemplate.tsx  Page shell: skip link, labelled navigation landmarks, footer
  types/Database.ts           Generated by `npm run db:types`; do not edit
  validations/                Zod schemas
supabase/
  config.toml                 Local stack configuration (not used by hosted projects)
  migrations/                 Ordered SQL migrations
  tests/database/             pgTAP tests (`npm run test:rls`)
tests/e2e/                    Playwright suites against the production build
```

## Request flow

1. `src/proxy.ts` runs for page requests (not `/_next`, `/api` or files). It creates a request-scoped Supabase client and calls `auth.getClaims()`, which refreshes an expired access token using the refresh token. Refreshed cookies are written to the request (so Server Components in the same request see them) and to the response, together with Supabase's `Cache-Control`/`Expires`/`Pragma` headers so CDNs do not cache session-bearing responses.
2. The `next-intl` handler then negotiates the locale and rewrites/redirects; it forwards the updated request headers.
3. Pages and layouts render on the server. Protected pages call `requireUserClaims()`; Server Actions validate input with Zod and call `requireUserClaims()` again before mutating.
4. Data access uses the publishable key with the user's JWT, so **Row Level Security is the final authority**. The app never uses the Supabase secret/service-role key.

The proxy does not authorize anything. Authorization lives in pages, actions and the database, because proxies can be skipped by other entry points (for example, Server Actions posting to a cached page).

## Authentication

- Identity checks use `getClaims()` (verifies the JWT signature, locally when the project uses asymmetric signing keys). `getSession()` is never trusted on the server.
- Sign-up returns a session immediately when email confirmations are off (the local default) and shows "check your email" when they are on.
- Email links (confirmation, password recovery) return to `/[locale]/auth/callback`, which exchanges the PKCE code in the same browser and redirects to `next`. `getSafeRedirectPath()` only allows same-origin paths, normalizing `\`, tabs and newlines like browsers do.
- Error messages do not reveal whether an account exists (sign-in errors are generic; password reset always reports success).

### Registration policy (decide per product)

Local `supabase/config.toml` enables public email sign-up with confirmations **off** so tests need no mail delivery. Hosted Supabase projects are configured in the dashboard, not by this file. Before launch, each product must decide and configure, at the **provider** level:

- whether public sign-up is allowed at all (`Allow new users to sign up`), or invite/admin-only;
- email confirmation, a real SMTP provider and branded templates;
- CAPTCHA (hCaptcha/Turnstile) and Auth rate limits;
- permitted providers and redirect URL allow-list (`Site URL`, additional redirect URLs).

Hiding the sign-up link does not prevent sign-ups through the Auth API. If a product disables sign-up in Supabase, the sign-up form shows "Sign-up is not available" for the `signup_disabled` error.

## Data and RLS

- `supabase/config.toml` sets `auto_expose_new_tables = false`: new tables are not reachable through the Data API until a migration grants access. Configure the same expectation for hosted projects and always write explicit `grant` statements.
- `public.profiles` is the only table: one row per auth user, `display_name`, timestamps (`moddatetime`). Anonymous users have no privileges; signed-in users can select/insert/update only their own row (`id = auth.uid()`); there is no DELETE grant (rows cascade with the auth user).
- `supabase/tests/database/profiles.test.sql` covers anonymous, owner and cross-user allow/deny cases.
- Workflow: write a migration (`npx supabase migration new <name>`, then edit the SQL), `npm run db:reset`, `npm run test:rls`, `npm run db:types`, commit the regenerated types. CI fails if types drift.

## Internationalization and accessibility

- Locales come from `src/utils/AppConfig.ts`; `[locale]/layout.tsx` sets `<html lang>`. Unknown paths render a localized 404.
- All user-visible strings live in `src/locales/*.json`. `npm run check:i18n` fails on missing, unused or undefined keys; Server Actions return translated messages so every key is statically visible.
- The shell provides a skip link, labelled `nav` landmarks, a single `h1` per page and a global `:focus-visible` outline. Forms use visible labels, `aria-invalid`, `aria-describedby` for hints and errors, and `role="alert"`/`role="status"` for results. Language switching uses links (not an auto-navigating select) with `lang`/`hrefLang`.
- Playwright runs axe (WCAG 2.0–2.2 A/AA rules) on public pages in both locales and on the signed-in page. Automated checks do not replace manual screen reader testing.

## React Compiler

`reactCompiler` and `turbopackRustReactCompiler` are enabled when `NODE_ENV=production` (`next build`) and disabled in `next dev` for faster rebuilds. Behaviour is the same; only memoization differs. The E2E suite runs the production build, so compiled output is what gets tested. Write plain components; reach for `useMemo`/`useCallback` only when profiling shows a need, and use effects only to synchronize with external systems.

## Observability

- `src/libs/Logger.ts`: JSON lines on stdout, no remote sink. `@logtape/redaction` removes fields that look like passwords, tokens, keys, auth data, emails, phones or addresses. Log error codes, never request payloads.
- Sentry: initialized only when `NEXT_PUBLIC_SENTRY_DSN` is set. Cookies, headers, bodies, URL query parameters, user info, DB query data and stack-frame variables are not collected; no Session Replay; 10% trace sampling. Source maps are generated, uploaded and deleted only when `SENTRY_AUTH_TOKEN` is present.

## Security defaults

- Secrets: the app needs none at runtime. Only `NEXT_PUBLIC_*` Supabase URL and publishable key are used. All env vars are validated in `src/libs/Env.ts`.
- Headers (all routes): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation off), `Strict-Transport-Security: max-age=63072000` (no `includeSubDomains`/`preload`; opt in per product), and a CSP with `base-uri`, `form-action`, `frame-ancestors`, `object-src`.
- **Script/style CSP is deferred**: a strict CSP for Next.js needs per-request nonces, which makes every page dynamic, and its `connect-src` depends on each product's Supabase/Sentry hosts. Add it when the product's hosts and rendering strategy are known.
- Rate limiting: Supabase Auth enforces its own limits (sign-in/sign-up, emails, token refresh, OTP) — configure them in the dashboard and consider CAPTCHA. Application mutations (currently only the profile update) are **not** rate limited. When products add abuse-prone mutations, use a shared store (database or platform/WAF limits); a per-process in-memory counter is not a valid distributed rate limiter.
- Dependencies: CI runs `npm audit --audit-level=high` and `npm audit signatures`; Dependabot proposes updates monthly. A green audit is not a security review.
